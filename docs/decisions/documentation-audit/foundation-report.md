## Current behavior worth explaining

- Inventory checks persisted organization ownership in its services and queries. Composite aggregate foreign keys additionally constrain organization/item/location/stock relationships. It is not tenant-agnostic in this application. Sources: `Services/InventoryService.php`, `Services/InventoryQueryService.php`, `Services/{Item,Location,Stock}/ManageInventory*Service.php`, `Support/OrganizationScopeResolver.php` in Shared, Inventory migration history.
- Inventory adapters link persisted host Eloquent models; their traits expose organization-constrained adapter relations. They do not expose stock totals directly. Existing adapter creation is idempotent by organization/morph identity and does not apply a new configuration to an existing adapter. Sources: Inventory contracts, traits, Item/Location management services and morph-relation tests.
- Quantities must convert to whole base units, with a ratio-1 base unit and a maximum of 10^12 base units per input line. Costs are integer minor units in the functional currency. Lot value is `remaining * unit_cost + cost_remainder`; the first deduction receives the entire remainder. Sources: `Validation/TransactionValidator.php:500`, `Services/InventoryService.php:829`, `:889`, `:1035`, quantity/cost tests.
- In/out lines require `type`. Transfer and adjustment prohibit it. Incoming currency/cost are required. Adjustment removes caller currency/cost fields, derives a positive increase's cost from remaining functional-currency stock, and treats quantity as a target. Sources: `Validation/TransactionValidator.php:94`, `:115`, `Services/InventoryService.php:630`.
- Idempotency uses organization/key uniqueness and a canonical hash of typed fields before FX conversion. List order and quantity string formatting remain significant. Validation runs before replay lookup, so current configuration can invalidate an old retry. Sources: `Services/TransactionPayloadHasher.php`, `Services/InventoryService.php:274`, `Data/MovementData.php`, idempotency tests.
- Previews run the real pipeline with Eloquent events suppressed, then roll back. They return void and do not reserve stock or return a quotation. Reversals create compensating entries, do not restore an old lot's remaining quantity for an OUT reversal, and do not support adjustments. Source: `Services/InventoryService.php:126`, `:143`, `:185`, `:219`, `:383`, `:435`; preview and reversal tests.
- Shared response shapes only govern relation loading. Resources own scalar fields; none mode does not invoke the resource factory. Cursor metadata has `per_page`, `next_cursor`, `prev_cursor`, no offset-page total. Sources: Shared Http/Responses, BaseCollection, deterministic cursor helper, response tests.
- Shared model aliases derive from singular table names and also form permission prefixes. Scope checks and permission checks are different operations. Sources: Shared registries, BasePolicy, OrganizationScopeResolver.
- Business numbering is PostgreSQL atomic allocation by organization and rendered visible identity with SEQ=0. Configuration keys with identical visible identity share the counter. `reset` validates necessary date tokens; actual identity changes define period boundaries. It uses the application clock. Source: `Services/BusinessNumberService.php`; regular and pcntl concurrency tests.
- State machines are frozen enum graphs and independent in-memory actors. They do not implicitly authorize, persist, lock, or dispatch domain events. Sources: Shared StateMachine classes and unit tests.

## Existing documentation contradictions

1. `app-modules/inventory/docs/getting-started.md:10` calls Inventory tenant-agnostic; current services, queries, policies, HTTP routes, and database constraints explicitly enforce organization boundaries. Drafts state the actual boundary.
2. `app-modules/inventory/docs/reading.md:7` documents `getItemStock`, `getLocationStock`, `listSummary`, `listExpiring`, `listMovements`, `listTransactions`; the current public service exposes `getItemLocationLots`, `paginateSummary`, `paginateStocks`, `paginateMovements`, `paginateTransactions`, `retrieveTransaction`. Drafts use those methods.
3. Inventory README incoming example omits movement `type`; `TransactionValidator::rules()` requires it for in/out. Draft examples include it.
4. `app-modules/inventory/docs/models.md:65` says business reference fields are optional. The current transaction validator requires both. The persisted `reference_id` column is UUID while its structural validation is only `string`; drafts instruct callers to use a UUID, without claiming an arbitrary string is persistable.
5. `app-modules/inventory/docs/models.md:67` and getting-started mention application summary methods; the current Inventory Resources do not embed host item/location descriptions via those methods. Drafts describe the actual scalar/optional-relation fields.
6. Root `docs/api/responses-and-errors.md:65` promises a universal `message` field and offset pagination at lines 87–103. Shared `ResponseResponder` and `BaseCollection` currently use resource/raw payloads and cursor metadata. Drafts document current shapes.
7. `.ai/rules/testing.md` references InventoryReadEndpointsTest as a real authenticated read example, but that file disables `Authenticate`, `ThrottleRequests`, `ResolveAuthContext`, and `SetTeamPermissionsId` before injecting an AuthContext. It exercises real Request/controller/service/resource/policy behavior with supplied context, not the complete authentication middleware stack. Do not present it as proof of that full stack.

## Implementation discrepancies for follow-up, without code changes

These findings do not change the documentation scope. Public pages state current behavior and avoid the unsupported promise.

- **HTTP clearing of stock metadata is rejected.** `UpdateInventoryStockMetadataRequest.php:23` declares `required|nullable|array`, while `ManageInventoryStockService::updateMetadata()` accepts nullable arrays. Laravel's implicit Required rule rejects null and empty arrays; Nullable only skips non-implicit rules. Sources also inspected locally: `vendor/laravel/framework/src/Illuminate/Validation/Validator.php:924`, `Concerns/ValidatesAttributes.php:2168`. Drafts explicitly distinguish the non-empty HTTP contract from the nullable PHP service.
- **OUT reversal FX evidence appears to be lost.** `InventoryService::buildReversalPayload()` passes historical `exchange_metadata` for incoming reversal lines (`:421`), but `TransactionValidator::rules()` does not whitelist that nested field. The validated input used by `MovementData::fromArray()` consequently lacks it. Transfer reversal's separate batch path preserves historical metadata. This is a source-level finding; no runtime test was executed. Drafts promise exact costs, currency/date/stock snapshot for OUT reversals, without claiming FX snapshot preservation.
- **Generated model scaffolds conflict with a current architecture guard.** `stubs/model.stub`, `model.pivot.stub`, `model.morph-pivot.stub` explicitly redeclare `incrementing` and `keyType` while using SharedTraits/HasUuids. `ModelIntegrityTest.php` has a test prohibiting that duplication. `MakeModel::buildClass()` only resolves the table after the parent generation; it does not remove these properties. Generated models also require real fillable/casts and domain migrations before satisfying integrity tests. Documentation says generated code is a starting point.
- **Request placeholder imports are not resolved for controller forms that use Request.** Root controller stubs contain `IlluminateHttpRequest`; Shared MakeController resolves JsonResponse and Response placeholders, but not Request. Installed parent controller/generator implementations do not resolve that custom token. The existing generation matrix uses a model controller and does not assert this Request case. No generation command was run, so no temporary source files were created.
- **Route format guard's digit range differs from its description.** `RouteNamingTest.php` uses `[a-z0-0.-]`, so only digit 0 is permitted, despite a message describing all lowercase alphanumeric route names. The current route convention is still documented as lowercase names with dots/dashes; this test discrepancy is reserved for follow-up.

## Questions à l'auteur

Les contrats actuels sont documentés sans attendre ces réponses. Ces questions servent à expliquer tes choix ou à distinguer une règle volontaire d'une limite actuelle. Les éléments entre « constat » et la question viennent du code ; les motivations ne sont pas déduites.

1. **Répartition du reste monétaire.** Constat : un lot de 3 unités pour 100,01 distribue 33,35 à la première sortie, puis 33,33 et 33,33. Pourquoi attribuer tout le reste à la première allocation plutôt que le répartir ? Est-ce une convention comptable ou une règle choisie pour assurer une conservation simple et déterministe ? Source : `app-modules/inventory/src/Services/InventoryService.php:889`.
2. **Politique d'expiration obligatoire.** Constat : FIFO explicite est refusé pour un article périssable, FEFO explicite pour un article non périssable ; Manual reste possible. Pourquoi interdire ces stratégies plutôt que simplement fournir un défaut ? Quelle situation métier cette contrainte évite-t-elle ? Sources : `Validation/TransactionValidator.php`, `Services/Item/ManageInventoryItemService.php`.
3. **Lots déjà expirés.** Constat : FEFO les place en premier mais ne bloque pas leur consommation ; les filtres « expire avant » les incluent. Souhaites-tu laisser volontairement l'interdiction à chaque processus métier ? Quelle règle utiliserait un module de vente ou de préparation ? Source : `Services/InventoryService.php:1067`.
4. **Ajustements sans remise à zéro.** Constat : quantité cible zéro est invalide et cible inchangée lève une exception ; une sortie peut pourtant vider le stock. Ces deux refus sont-ils des règles métier durables ou des limites de la première version ? Source : `Validation/TransactionValidator.php:142`, `Services/InventoryService.php:630`.
5. **Valorisation des hausses d'inventaire.** Constat : il faut du stock fonctionnel existant pour calculer la moyenne, caller coût/devise sont supprimés. Comment souhaites-tu traiter la première découverte d'un stock physique ou une correction quand il ne reste aucun lot ? Pourquoi ignorer les champs plutôt que les rejeter ? Sources : `Services/InventoryService.php:1035`, `Validation/TransactionValidator.php:94`.
6. **Lignes non suivies et transactions vides.** Constat : les lignes d'articles dont le suivi est désactivé disparaissent avant la validation, et une transaction vide peut être conservée. Quel cas d'usage motive la conservation de cet en-tête ? Veux-tu expliquer pourquoi une ligne incorrecte mais non suivie ne provoque pas d'erreur ? Source : `Validation/TransactionValidator.php:60`.
7. **Idempotence et configuration courante.** Constat : la validation précède la recherche de transaction existante. Une reprise peut donc échouer si l'article ou l'emplacement change depuis le succès initial. Ce comportement est-il intentionnel ? La garantie attendue est-elle « même opération acceptée dans le contexte actuel » ou « restituer tout succès historique connu » ? Source : `Services/InventoryService.php:274`.
8. **Équivalence des reprises.** Constat : « 1 » et « 1.0 » pour quantity peuvent donner des hash différents ; l'ordre des lignes et lots reste significatif. Veux-tu privilégier la fidélité au payload original ? Quels changements doivent être considérés comme une nouvelle opération ? Source : `Services/TransactionPayloadHasher.php` et `Data/MovementData.php`.
9. **Compensations et immutabilité.** Constat : les services exposent des compensations, mais les modèles journaux ont des champs remplissables et aucune interdiction SQL générale de mise à jour. Le contrat est-il seulement de ne pas modifier le journal par les services publics, ou souhaites-tu une immutabilité plus forte à terme ? Sources : Inventory modèles transaction/movement et service de reversal.
10. **Décalages de contrat à trancher.** Constat : PATCH ne peut actuellement effacer metadata malgré un service nullable ; l'annulation OUT semble perdre le snapshot FX. Souhaites-tu conserver ces limites dans la première publication ou en faire des correctifs séparés ? Sources : les deux écarts décrits plus haut. Aucune modification du code n'a été faite.
11. **Identité visible de numérotation.** Constat : deux clés de configuration ayant le même format rendu partagent un compteur ; restaurer un ancien format reprend son compteur. Quel usage concret motive cette identité plutôt qu'un compteur par clé/document ? Source : `app-modules/shared/src/Services/BusinessNumberService.php`.
12. **Signification de reset.** Constat : reset valide les tokens nécessaires mais le format peut produire une période plus fréquente (yearly + MONTH), et never + YEAR change chaque année. Veux-tu expliquer reset comme une exigence minimale du format, ou devrait-il à terme représenter une cadence exacte ? Source : `BusinessNumberService.php:154`.
13. **Horloge de l'organisation.** Constat : numérotation et jours restants utilisent l'horloge de l'application ; la convention générale du projet distingue dates civiles d'organisation et timestamps UTC. Quelle timezone doit décider d'un changement de jour/année pour une organisation située ailleurs ? Sources : BusinessNumberService, InventoryStockResource, InventoryStockFilterRequest, `.ai/rules/date-time-conventions.md`.
14. **Réponse 204 par défaut.** Constat : les mutations ordinaires répondent sans corps et la représentation est une option ; certaines opérations IAM font exception. Quel objectif d'usage ou de performance a conduit à ce choix ? Source : `app-modules/shared/src/Http/Responses/ResponseContract.php`.
15. **Formes limitées aux relations.** Constat : la configuration de `fields` est rejetée et les Resources gardent la maîtrise des scalaires. Pourquoi ce découpage plutôt que plusieurs projections de champs ? Source : Shared Http/Responses/ResponseShape et ResponseContractRegistry.
16. **Alias dérivés des tables.** Constat : la même identité singulière sert aux morphs et préfixes de permissions. Pourquoi lier ces identités au nom de table plutôt qu'à un alias métier explicitement déclaré ? Comment souhaites-tu gérer un renommage de module/table ? Sources : Shared MorphMapRegistry et BasePolicy.

## Architecture and registry guarantees for contribution docs

| Guard | What it checks | Material scope limit |
| --- | --- | --- |
| ModularDependencyTest | Declared module graph, no HTTP Resource imports in Services, Library attachment boundary, no main App logic imports. | Mostly source-string scans. Shared helpers and discovery files have explicit exceptions; runtime container resolution and dynamic class strings are not a complete import graph. |
| ModelIntegrityTest | Schema casts, UUID/factory/soft-delete traits, fillable, modern accessors, explicit table, existing factories. | Uses discovered models and configured ignore lists; requires refreshed PostgreSQL schema. It cannot replace behavioral invariants. |
| DatabaseIntegrityTest | Primary keys, JSONB, bigint quantities, tenant columns/uniqueness, FK index support, partial soft-delete indexes, morph-pair indexes. | Reads actual test schema with explicit exceptions in model-integrity config. FK index support accepts either a composite prefix or separate leading-column indexes; it does not assert every possible query's optimal index or every tenant FK. |
| MorphMapTest and MorphMapCacheTest | Discovered model registrations, alias formation, cache generation/clear, discovery outside production and cache loading in production. | Tests cache behavior using synthetic maps. Changes still require deployment regeneration and consideration of persisted old morph values. |
| ResponseContractTest and ResponseContractCacheTest | API route coverage/no stale definitions, selected relation definitions/IAM exceptions, cache flattening and environment behavior. | Configuration consistency does not prove every HTTP Resource/policy/service behavior. Integration/endpoint tests remain necessary. |
| NestedResourceRouteScopingTest | Exhaustive current classification of multi-binding routes as scoped children or explicit Inventory independent pair. | Verifies route configuration; domain tenant isolation and authorization still need HTTP/integration tests. |
| LocalizationIntegrityTest | Literal referenced module English keys exist, files return arrays with strict header, Laravel placeholder style. | Regex extracts literal calls; it does not enumerate dynamically assembled keys, guarantee FR API runtime, or validate translation semantics. |
| ResourceOrganizationExposureTest / ResourceUserExposureTest | Forbid organization_id token in ordinary Resource source; constrain UserResource references to an allow list. | Lexical checks, with deliberate account-owner exception. They do not exhaustively inspect computed JSON or every sensitive field. |
| AssertionExceptionContractTest / NoBareExceptionThrowTest | Concrete module exceptions extend AssertionException; module source contains no directly spelled bare Exception throws. | Class discovery/regex patterns are targeted and do not prove all dynamic/inherited exception behavior. |
| GeneratorCommandsTest / FactoryDiscoveryTest | Module generation paths/selected output content and factory resolution. | Generated placeholders are not completed business code; factory discovery dataset is five selected models. Current generator tests do not expose every stub contradiction listed above. |
| OptionalDevelopmentProvidersTest | Provider list loads without optional development package and includes Telescope when installed. | Does not prove an entire production no-dev boot/deployment. |

Root stubs consistently provide strict headers and typed methods for scaffolding. Requests return authorize=true and an empty rules array; controllers are empty response scaffolds; factories and Pest tests are placeholders; migration.create only provides UUID id/timestamps. None constitutes a completed secure endpoint or domain module. This distinction belongs in contribution documentation.
