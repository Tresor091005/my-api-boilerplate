# Findings of 2026-11-15: rules that block

Working note, not a decision. It records what a read of every business
refusal of the codebase found, so each point can be settled later. Nothing
here was fixed.

## How to read it

- **Scope.** About 280 refusals in 10 modules were read. The question was:
  can two features block each other so that the user cannot go on? Most of
  what came out is something else (a missing feature, a message that does not
  help, a bug); it is kept here anyway, in separate parts.
- **Where the code is.** Parts 1, 3, 4 and 5 describe behaviour that is on
  `main`. Part 2 describes the branch `catalog-prices` (prices that contain
  taxes), not merged when this note was written. The line numbers are those of
  the `catalog-prices` working tree on that day; on `main` a few can be off by
  some lines.
- **Checked.** `[checked]` means the point was read again in the code by the
  main reviewer. The others come from one parallel read each and were not read
  a second time. Nothing was run. `(not run)` and `(unverified)` are kept from
  those reads.
- **Verdict.** What the owner decided on 2026-11-15, where a verdict was given.
  Without a verdict the point is open and can wait.

## 1. Features that block each other

### 1.1 Leaving a plan freezes the stock of bundles

An organization assembles bundles: components leave the stock and the bundle
gets stock. Taking a bundle apart again ("detach") and transferring bundle
stock both need the plan feature `catalog.bundle_assembly`, when the operation
is drafted and when it is completed. After the organization moves to a plan
without that feature, its bundle stock is stuck: the bundle cannot be taken
apart, so its composition cannot change, it cannot be deleted, and its
components cannot be deleted either. The way out is to buy the feature again.
The gating is documented as deliberate; the frozen stock is not.

- `app-modules/catalog/src/Services/BundleStockOperationService.php:55, 101-102`
- `app-modules/catalog/src/Services/StockTransferService.php:217-219, 300-302`
- `app-modules/catalog/src/Services/BundleService.php:437-446`
- `docs/modules/billing.md:31-38`

Possible fix: leave "detach" out of the feature; only assembling sells it.

### 1.2 A deactivated stock location can trap its stock

A stock location that still holds stock can be deactivated with no check. The
plan limit `catalog.stock_locations` counts active locations and is checked
when one is reactivated, and a transfer needs both locations active. At the
limit, the location cannot be reactivated, so its stock can be neither moved
nor removed, and the location cannot be deleted. With an allowance of one
active location it stays so until an upgrade. Plan allowances are data: not
checked.

- `app-modules/catalog/src/Services/StockLocationService.php:83-93`
- `app-modules/catalog/src/Services/StockTransferService.php:180-209`
- `app-modules/inventory/src/Services/Location/ManageInventoryLocationService.php:47-61`

Possible fix: refuse deactivating a location that holds stock, or allow
transfers out of an inactive location.

### 1.3 A blocked organization cannot give someone the right to pay

Without a subscription every `auth.api` route answers 403, except a pinned list
of routes. Starting a checkout needs `billing_subscription.pay`, which only the
owner holds by default. Every route that manages roles and members is behind
the same gate, so while the organization is blocked nobody can be given that
right. If the owner is away, nobody can pay.

- `bootstrap/app.php:41-48`
- `app-modules/iam/routes/iam-routes.php:75-90`
- `app-modules/billing/src/Http/Controllers/CheckoutController.php:34`

Possible fix: exempt the routes needed to grant a role, and extend the pinned
list test.

### 1.4 A variant or bundle that holds stock can never be deleted `[checked]`

No endpoint brings stock in or lowers it. The only writes are stock transfers
and bundle operations, which move or convert stock (stock exists today through
the demo seeder only). With stock on hand, a variant cannot be deleted, its
stock tracking cannot be switched off, and the last location holding stock
cannot be deleted. For a bundle component it is a loop: deleting the variant is
refused because a bundle uses it, removing it from the bundle is refused while
the bundle has stock, and taking the bundle apart gives the variant its stock
back.

- `app-modules/inventory/routes/inventory-routes.php:16-25`
- `app-modules/catalog/src/Services/TransactionalCatalogItemService.php:239-250`
- `app-modules/catalog/src/Services/BundleService.php:298-300, 437-446`
- `app-modules/inventory/src/Services/Item/ManageInventoryItemService.php:70-72, 152-154`

**Verdict: not a problem.** Stock in and out arrive with procurement and sale.
When they do, a write-off must exist before or with the first stock-in.

### 1.5 A file cannot be detached from an inactive customer or service `[checked for customers]`

Deleting a Library file is refused while it is attached, and the message asks
to detach it. But detaching is refused on an inactive customer or service: the
check on activity runs for removals too, with the message "Files cannot be
attached to an inactive customer". Deactivating a record that has files is
accepted with no warning. The way out today: reactivate, detach, deactivate
again.

- `app-modules/customer/src/Services/CustomerFileService.php:27-28`
- `app-modules/catalog/src/Services/CatalogFileService.php:43-60, 67-83`
- `app-modules/library/src/Services/FileService.php:222-224`

Possible fix: check activity only when a file is added.

### 1.6 A label attached to a deleted variant can never be deleted `[checked]`

Deleting a variant, or its product, leaves its label links in
`master_labelables`: nothing detaches them. Deleting a label is refused while
any link exists. The variant is soft-deleted and cannot be restored, so nothing
can remove the link.

- `app-modules/catalog/src/Services/Variant/TransactionalProductVariantService.php:107-120`
- `app-modules/master/src/Services/LabelService.php:142-154`

**Verdict: to fix.** Detach the labels when a variant is deleted; the label
deletion could also ignore links whose record is deleted.

### 1.7 A role offered by a pending invitation can be deleted or deactivated

Deleting a role only checks members. An invitation that offered the role then
fails when it is accepted or sent again (`roles_unavailable`); the guest is
told to "replace the invitation roles", which only an administrator can do.
An invitation can also offer an inactive role: accepting succeeds, but the
member has no usable role and the organization does not show in
`GET /v1/auth/me`, with no message.

- `app-modules/iam/src/Services/RoleService.php:129-139`
- `app-modules/iam/src/Services/InvitationService.php:114, 193, 286-297`
- `app-modules/iam/src/Http/Requests/InvitationRolesRequest.php:17-23`

Possible fix: refuse the deletion like `role.assigned`, or drop the role from
pending invitations; check `is_active` on offered roles.

### 1.8 Deactivating or deleting a stock location breaks its transfers later

A stock location is deactivated or deleted with no check. Afterwards, creating
or editing a draft transfer with that location answers 404; completing a draft
answers `location_inactive`, or 404 if the location was deleted; cancelling a
completed transfer fails on `movements.N.location_id`, a field the caller never
sent, and for ever if the location was deleted. Drafts also accept inactive or
untracked items and fail only when they are completed.

- `app-modules/catalog/src/Services/StockLocationService.php:79-111`
- `app-modules/catalog/src/Services/StockTransferService.php:116-141, 185-206, 279-286`
- `app-modules/inventory/src/Validation/TransactionValidator.php:264-305`

Possible fix: answer `location_inactive` instead of 404, check the locations
before cancelling, and run the completion checks when a draft is written.

### 1.9 Cancelling a completed transfer whose stock was used

Any use of a lot at the destination, even partial, blocks the cancellation for
good (`reversal_stock_already_used`). This is intended and tested. The way out
is a new transfer in the other direction, which the error does not say, and
which counts against the `catalog.stock_transfers` allowance.

- `app-modules/inventory/src/Services/InventoryService.php:259-272, 776-784`
- `app-modules/inventory/docs/reversals.md:3`

### 1.10 A note that had a reply can never be deleted `[checked]`

The relation counting replies includes deleted ones, so deleting every reply
does not free the root note; a test asserts it. Replies the caller cannot see
count too. Such a note also keeps one of the 20 note slots of its record.

- `app-modules/master/src/Models/Note.php:126-132`
- `app-modules/master/src/Services/NoteService.php:141-142, 201-202`
- `tests/Feature/NotesIntegrationTest.php:91-139`

**Verdict: probably should be possible**, the user would not understand the
refusal. Read the code again before deciding. Not now.

### 1.11 The cap of 20 notes per record counts notes the user cannot see

The limit counts every root note of a record. Other members' private notes are
hidden from the list and cannot be deleted, even with `master_note.delete`;
expired notes stay hidden for 30 days before they are pruned. The refusal says
"remove some first" with nothing visible to remove.

- `config/child-limits.php:62-63`
- `app-modules/master/src/Policies/NotePolicy.php:34-41`
- `app-modules/master/src/Services/NoteService.php:39-42, 196-200, 372-385`

### 1.12 A label group above 100 labels can no longer be reordered

The reorder call must list every label of the group but accepts 100 ids at
most, and nothing limits the labels of a group. The only way out is deleting
labels, which meets 1.6.

- `app-modules/master/src/Http/Requests/LabelReorderRequest.php:17`
- `app-modules/master/src/Services/LabelService.php:94-107, 307-345`

### 1.13 Restoring a file can be refused by the folder limit `(not run)`

Restoring a file also restores its deleted folders. If the parent already has
50 folders the restore is refused, and a file in the trash cannot be moved
first.

- `app-modules/library/src/Services/FileService.php:252, 259-301`
- `config/child-limits.php:53-56`

### 1.14 A draft bundle stock operation cannot be changed, cancelled or deleted `[checked: routes]`

The routes are list, create, show and complete. A draft whose bundle changed,
or whose location was deleted, stays a draft for ever. It blocks nothing.

- `app-modules/catalog/routes/catalog-routes.php:71-80`
- `app-modules/catalog/src/Services/BundleStockOperationService.php:397-425`

### 1.15 Checked and without a dead end

- Tax profile, items and prices (see part 2): each refusal has a way out that
  the tests prove.
- Deleting a tax or a profile, changing a tax used by profiles: the blocking
  lines can always be removed first.
- Categories, options, option values, last variant of a product, bundle of two
  items: each has a direct way out.
- Stock location limit: deactivating and deleting an empty location are never
  refused, so an organization at its limit can get under it.
- Draft stock transfers: never stuck, they can be edited or deleted.
- Folders, file slots, storage quota, addresses and contacts: deleted rows do
  not count, removing is always possible.
- Roles assigned to members, invitations already accepted, subscription rules:
  each has a route out, sometimes badly named (see part 4).

## 2. Prices that contain taxes (branch `catalog-prices`)

No dead end and no loop. What remains:

### 2.1 The records that block are hard to find `[checked]`

No list can be filtered to find the prices of a price level, the prices that
contain a given tax, the items using a tax profile, or the customers of a price
level. So the refusals `price_level_in_use`, `profile_in_use`,
`included_taxes_in_use` and "the new profile does not suit the prices" have a
way out that means reading the whole catalog. `price_level_in_use` also gives
one message for two causes (prices, customers).

**Verdict: settle it with read endpoints.**

### 2.2 An old tax left in a price can refuse a change of profile

A tax that leaves a profile stays listed in the prices and is ignored when the
item is sold. If the item then takes another profile, that old entry makes the
change refused until the list of the price is cleaned.

### 2.3 A fixed tax raised above a price that contains it

Changing the amount of a tax is never refused. A price lower than the fixed
taxes it contains is refused later, when it is sold or changed
(`amount_below_included_taxes`).

### 2.4 A customer tied to a price level in a disabled currency `(unverified)`

Disabling a currency checks nothing. Its price levels stay, unusable, and a
customer sold only at such a level could not be sold to. To settle with the
sale.

- `app-modules/organization/src/Services/OrganizationSettingsService.php:40-58`

## 3. Missing features and intended dead ends

### 3.1 No stock write-off

See 1.4. Related, in the inventory service and without a route yet: an
adjustment cannot target 0, cannot raise a stock from 0 because no average cost
exists, and cannot be reversed; expired stock cannot be written off.

- `app-modules/inventory/src/Validation/TransactionValidator.php:94-113, 142`
- `app-modules/inventory/src/Services/InventoryService.php:392-407, 642-665`

### 3.2 A unit is never deleted or deactivated `[checked]`

Only `GET /v1/master/units` and `POST /v1/master/units/upsert` exist, and a
unit has no active flag. A unit created with a wrong ratio stays, and keeps
that ratio taken. At 100 units in a group the refusal says "remove some
first", which is impossible. Two messages are never used
(`unit_base_deactivation`, `unit_active_limit`), and
`docs/features/catalog-units.md:64-65, 111-112` still describes `is_active`
and a limit of 10 active units.

- `app-modules/master/routes/master-routes.php:32-33`
- `app-modules/master/src/Exceptions/UnitException.php:14, 29`
- `config/child-limits.php:66`

**Verdict: keep the behaviour**, 100 units in a group is enough. Only the
message is wrong: say the limit is reached.

Related: a built-in unit group takes no custom unit, and an item never changes
unit group, so an item created in a built-in group can only be priced in
built-in units (`app-modules/master/src/Http/Requests/UnitUpsertRequest.php:29-35`).

### 3.3 Ownership of an organization cannot move `[checked]`

`owner_id` is written once, at creation. The owner cannot be removed or
deactivated and keeps the Administrator role, which nobody else can receive.
If the owner loses access, the organization depends on its custom roles.

- `app-modules/organization/src/Services/OrganizationService.php:33-37`
- `app-modules/iam/src/Services/OrganizationMemberService.php:58-60, 86-88`
- `app-modules/iam/src/Services/MemberRoleDeletionService.php:67-72`

**Verdict: intended for now.** Less important than stock in and out.

Related, small: a member cannot leave an organization alone (the limit of 50
memberships says "remove some first"), and a linked Google identity cannot be
unlinked.

### 3.4 The SKU of a deleted item stays reserved

Deliberate and tested. The answer is a clean 422, but the message does not say
a deleted item holds the SKU.

- `app-modules/catalog/database/migrations/2026_08_31_091049_create_catalog_items_and_share_product_variant_identity.php:29`
- `app-modules/catalog/tests/Feature/ProductServiceTest.php:241`

**Verdict: only the message. Not a problem yet.**

### 3.5 A checkout cannot be paid in production

The confirmation is a console command registered outside production; there is
no route or webhook. A plan priced 0 also gives a checkout of amount 0.

- `app-modules/billing/src/Services/CheckoutService.php:75-112, 127-140`
- `docs/modules/billing.md:119-121, 156-158`

**Verdict: known.**

### 3.6 The functional currency never changes

Intended and documented. There is no update path, and a
`functional_currency_code` sent to the settings is ignored without a word.

## 4. Messages that do not say what blocks, or how to get out

### 4.1 In production the detail of an error is empty `[checked]`

`errors.context` is null in production, a documented choice. Many refusals name
what blocks only there: an option used by variants, an item used by a bundle,
a tax used by profiles, a price level in use, a role assigned, a file
attached, a label in use, the table that reached its limit.

- `bootstrap/app.php:68`
- `docs/api/responses-and-errors.md:138`

Possible fix: let each exception declare the context keys that are safe to
show (ids, codes, counts), as the billing exceptions already do with their own
`render()`.

### 4.2 One message for several causes

- `stock_transfer_invalid_state`: one message for 7 causes; it is wrong for
  `same_location`, `duplicate_line`, `unit_invalid` and `transaction_missing`.
- `bundle_stock_operation_invalid_state`: one message for 5 causes; for an
  inactive location it talks about the bundle and its components.
- `price_level_in_use` (see 2.1) and `plan.in_use` (three causes).

- `app-modules/catalog/src/Services/StockTransferService.php:183-292`
- `app-modules/catalog/src/Services/BundleStockOperationService.php:191-227, 432-437`

### 4.3 Inventory messages show `:item_id` as written `[checked]`

`item_has_active_stock`, `item_cannot_delete_with_active_stock`,
`location_cannot_delete_with_active_stock` and
`reversal_item_tracking_disabled` have a placeholder in their text, but the
exception gives no value for it.

- `app-modules/inventory/src/Exceptions/InventoryItemException.php:13-24`
- `app-modules/inventory/src/Exceptions/InventoryLocationException.php:13-16`
- `app-modules/inventory/resources/lang/en/exceptions.php:23-25, 29`

### 4.4 No list finds the blocking records `[checked: filters]`

- Variants using an option or an option value: no filter; the context is the
  option's own id.
- Bundles using an item: no filter, and the refusal does not name the bundle.
- Deleting a product stops at the first variant that blocks.
- Records carrying a label: only a count; the documented
  `GET /v1/master/labelables/{type}/{id}/labels` is not routed. The last label
  of a group may also be impossible to remove, an empty list being rejected
  `(not run)`.
- Records a file is attached to: nothing, and detaching needs `update` on each
  record.
- Members holding a role: no filter, no count on the role.
- Stock of a stock location: the location does not show its inventory id,
  which is the only filter of the stock lists; stock rows give the inventory
  id and SKU, never the catalog id.

### 4.5 Hints that point to something unavailable

- `change_requires_active_subscription` and `change_to_same_plan` say "renew
  it instead"; renewing is refused in several states.
- `remaining_value_covers_price` says "choose it for the next period
  instead"; that is refused when the plan is paid beyond its period.
- `effective_rate_immutable` does not say the correction is a new rate with a
  later date; a rate created with an earlier date is accepted and never used.
- `organization_quota_exceeded` gives no figure, and neither the usage nor the
  quota is exposed.
- `limit_reached` on the 30-day transfer count does not say when room comes
  back; `currency_mismatch` on a plan change gives no hint.
- A reply is refused as soon as the root note has any expiry date, even in the
  future, with "An expired note cannot receive replies"; changing the
  visibility of a collective note answers a bare 403.
- A member whose role or membership was deactivated gets a bare 403 and the
  organization disappears from `GET /v1/auth/me`.

## 5. Bugs seen on the way

### 5.1 A service accepts any unit group `[checked]`

`ServiceCreateRequest` checks `unit_group_id` with `BulkExists`, a rule that
only works on lists and returns at once for a single value. An unknown id ends
in a database error (500); the id of a unit group of another organization is
accepted. After that every price of the service is refused, and the unit group
cannot be changed.

- `app-modules/catalog/src/Http/Requests/ServiceCreateRequest.php:50-56`
- `app-modules/shared/src/Rules/BulkExists.php:53-55`

Fix: `Rule::exists('master_unit_groups', 'id')` limited to built-in or own,
non-deleted groups.

### 5.2 Database errors answered 500

- A generated SKU is not checked: a collision, deleted items included, is a
  unique violation. Rare. Two simultaneous creations with the same SKU hit it
  too (`app-modules/shared/src/Support/SkuGenerator.php:15-27`).
- Two new units with the same name in one upsert get the same code
  `(not run)` (`app-modules/master/src/Services/UnitService.php:124, 134-138`).
- The checkout list after a plan was deleted reads a soft-deleted plan version
  `(unverified)` (`app-modules/billing/src/Http/Resources/CheckoutResource.php:21-39`).
- An exchange rate with more than 18 integer digits overflows its column
  `(unverified)` (`app-modules/organization/src/Services/ExchangeRateService.php:74-80`).

### 5.3 Wrong status or late check

- An inactive location on a transfer is a 404 though the request accepted it
  (`app-modules/catalog/src/Services/StockTransferService.php:185-203`).
- Draft transfer lines are only checked for shape; they fail when completed,
  on `movements.N.*` keys instead of `lines.N.*`. `stock_ids` given with a
  strategy that is not manual are validated, then ignored
  (`app-modules/catalog/src/Http/Requests/StockTransferRequest.php:30-37`).
- `bundle_system_unit_group_missing` is a setup fault answered as a 422 the
  user cannot fix (`app-modules/catalog/src/Services/BundleService.php:341-360`).
- A plan whose interval equals the advance limit (12 months) cannot be renewed
  before it ends (`app-modules/billing/src/Services/CheckoutService.php:319-324`).
- Starting a checkout cancels the pending one, so a preview cancels a payment
  in progress; an open question already listed in `docs/modules/billing.md:165-166`.

### 5.4 Possible race `(unverified)`

Inventory drops the movements of an untracked item without a word. If stock
tracking is switched off on a component between the check and the stock-in of
a "detach", the bundle stock is consumed and the lot of that component is
never created.

- `app-modules/inventory/src/Validation/TransactionValidator.php:36, 60-92`
- `app-modules/catalog/src/Services/BundleStockOperationService.php:152-161, 182-229`

### 5.5 Units: cache

A unit row deleted outside the API is guarded by nothing: prices, per-unit
taxes, bundles and inventory fail later. A built-in unit added by a deployment
stays unknown to an organization until its 24-hour unit cache expires, while
request validation already accepts it.

- `app-modules/master/src/Support/UnitCache.php:15, 46-52, 126-132`
